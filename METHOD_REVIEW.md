# Перевірка методу до виконання test

Окрема сесія `/root/holdout_method_review` прочитала POLICY, PROTOCOL та код реалізацій/оцінювання, не читаючи test, judge packet, мітки чи результати. Правок і виконання не робила. Блокуючих дефектів для валідних POLICY-входів не виявила.

Підтверджено повний stateful baseline з окремим reducer, однакові події й коректні знаменники primary metrics та sensitivity. Незалежність розроблення підтверджується розподілом сесій, а не лише двома назвами файлів.

Зауваження та врахування:

1. Обидва плеча реалізують спільну впорядковану політику. Тест досліджує її відповідність та еквівалентність реалізацій; superiority не випливає навіть із нульових порушень.
2. Frozen evaluator не включає повну валідацію типів. До першого запуску test окремий `check_data.py` доповнено перевіркою типів/діапазонів settings і identity. Цей checker не є частиною implementation freeze; політику, реалізації, evaluator і корпус не змінювали. Структурна перевірка не обчислює labels.
3. Окремо звітувати спільні insufficient_information, а не тільки незгоди суддів.
4. Середня затримка охоплює лише завершені reviews; незавершені/прострочені запити не включено. Це не загальна service latency.
5. Унікальні family tags не доводять новизну чи статистичну незалежність. Підстава для prospective holdout — freeze до створення корпусу окремим агентом; примітиви політики спільні.
