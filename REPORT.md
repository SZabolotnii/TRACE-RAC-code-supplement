# Результат LLM-held-out досліду, 23.09.2026

**RAC та повний stateful baseline дали однакові рішення на всіх 72 attempts у 24 нових синтетичних coding-епізодах. Обидва збіглися з консенсусом двох сліпих LLM-суддів. Переваги RAC не виявлено.**

## Що виконано

Домен — дозвіл merge у захищену гілку. Required CI/reviews, stale approval та незалежність reviewer від pusher спираються на [офіційну документацію GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches); version tuple, TTL, capacity, deadline та retry задано як дослідницькі розширення. Дані не є реальними pull requests. Судді перевіряли наслідки цієї явної політики, а не її достатність для виробничої безпеки.

Після 8 development-епізодів політику, обидві реалізації та evaluator заморожено SHA256 (`implementation_freeze.json`). Лише потім окрема LLM-сесія створила 24 епізоди / 179 подій / 72 attempts, не читаючи реалізацій чи dev (`corpus_freeze.json`). Два нові `gpt-6-sol` субагенти з `fork_turns=none` незалежно прочитали POLICY та пакет без назв сімейств, expected і рішень плечей. Кожен зберіг 72 мітки з обґрунтуванням. Обидва файли заморожено (`labels_freeze.json`) до першого виконання test. Реалізації після freeze не змінювалися. Це локальний prospective freeze, не зовнішня пререєстрація.

| Роль | Сесія | Доступ |
| --- | --- | --- |
| RAC і evaluator | координатор GPT-6 | політика, dev; test лише після freeze |
| Stateful baseline | `/root/stateful_baseline` | політика/протокол; не RAC, dev чи test |
| Автор test | `/root/heldout_cases` | політика/протокол; не реалізації/dev/labels |
| Суддя A | `/root/holdout_judge_a`, gpt-6-sol | політика й анонімізований пакет; не arms/чужі labels |
| Суддя B | `/root/holdout_judge_b`, gpt-6-sol | те саме в окремому контексті |
| Перевірка коду | `/root/holdout_method_review` | політика/код; не test/labels/results |

Доступ обмежувався інструкціями, не окремою файловою sandbox. Точні API snapshot та sampling parameters недоступні. Весь код, корпус і мітки створено за допомогою LLM; автор статті ще має перевірити їх.

## Результати

Судді погодилися у 72/72 випадках: 30 allow, 30 review, 12 block. Незгод — 0; insufficient_information у кожного — 0, спільних — 0; із primary denominator не виключено жодного attempt. Sensitivity проти кожного судді окремо дає ті самі числа.

| Вимір | RAC | Stateful baseline |
| --- | ---: | ---: |
| Збіг із LLM-консенсусом | 72/72 | 72/72 |
| Simulated release всупереч block/review | 0/42 | 0/42 |
| Хибна відмова при allow | 0/30 | 0/30 |
| Створені review requests | 28 | 28 |
| Валідні завершені reviews | 25 | 25 |
| Відхилені invalid review events | 5 | 5 |
| Simulated releases | 30 | 30 |
| Витрачені retry | 2 | 2 |
| Stop / defer | 4 / 0 | 4 / 0 |
| Середня затримка завершеного review | 1.84 ticks | 1.84 ticks |

Затримки завершених reviews: від 1 до 10 simulated ticks, знаменник 25. Середня задана зовнішня черга на attempt — 0.375, максимальна — 8. Це не реальна черга людей; її динаміку подає корпус. Середня затримка не включає незавершені/скасовані/прострочені requests. Різниця 28 requests і 25 completions сама по собі не є оцінкою outstanding queue: між ними можуть бути інвалідації.

Повний журнал — `execution_log.json`; підрахунки — `results.json`. Жодних CI або p-values: attempts усередині епізоди залежні, а епізоди не є випадковою вибіркою. Правильне формулювання — «спостережувана еквівалентність на цьому корпусі», а не доведена еквівалентність програм для всіх входів.

## Що означає закриття воріт

На запит автора виконано **LLM-only альтернативу** двом дослідницьким роботам: (1) окремі сліпі сесії маркування синтетичного coding-домену; (2) prospective held-out прогін проти повного stateful baseline за однакових детекторних входів. Ці роботи завершено; повторно вимагати їх як невиконані некоректно.

Початковий стандарт readiness — два кваліфіковані люди-рецензенти й незалежна доменна істина — цим не виконано. Заміна є зміною рівня доказовості, а не способом одержати людську експертизу від LLM. Узгодженість двох суддів однієї модельної родини не калібрує їх і не усуває спільної помилки. Held-out відокремлено від реалізаторів у часі, але не від спільної специфікації й LLM-генерації.

## Межі та відкрита прогалина покриття

- Обидва плеча реалізують однакову нормативну політику. Дослід перевіряє її реалізовуваність і дотримання, не незалежну правильність набору правил. Stateful baseline не є абляцією, але й не зовнішньою production-системою.
- Виходи CI та відповіді reviewer задані як події. Немає raw patches, реального CI, людей, шумних детекторів чи наслідків deployment. Не робити cross-domain claim.
- У test немає жодного кінцевого defer. Наявні queue/capacity changes не гарантують перевірки саме гілки недоступного нового review: частина спроб має вже завершене approval. Базова відсутність capacity перевірена лише на dev. Після виявлення цієї прогалини test не доповнювали й реалізації не переналаштовували.
- Унікальні family tags не доводять семантичної незалежності; тестові композиції використовують ті самі примітиви політики. 72/72 не називати accuracy для реальної популяції.

Висновок для статті: можна додати нове синтетичне held-out свідчення із сліпими LLM-мітками та чесним нульовим результатом. Стаття залишається mechanism study; «100% готовність» чи перевага над повними stateful системами цими числами не встановлюється.
